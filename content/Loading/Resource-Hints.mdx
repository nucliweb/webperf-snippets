# Resource hints

Analyzes resource hints on the page, checking for proper usage and identifying optimization opportunities. Resource hints help the browser prioritize resource loading for better performance.

### Resource hint types

| Hint | Purpose | When to Use | Priority |
|------|---------|-------------|----------|
| **preload** | Load resource for current page | Critical CSS, fonts, hero images, LCP | Highest |
| **modulepreload** | Preload ES modules | Critical JavaScript modules | High |
| **preconnect** | Establish early connection | Third-party origins you'll fetch from | High |
| **dns-prefetch** | Resolve DNS early | Third-party origins (fallback for preconnect) | Medium |
| **prefetch** | Load resource for next navigation | Resources needed on likely next page | Low |
| **prerender** | Pre-render entire page | High-probability next navigation | Lowest |

### Loading priority

```
preload/modulepreload → preconnect → dns-prefetch → prefetch → prerender
     (current page)                                    (future navigation)
```

### Common mistakes

| Mistake | Impact | Solution |
|---------|--------|----------|
| Preload without `as` | Browser can't prioritize | Add `as="script"`, `as="style"`, etc. |
| Font preload without `crossorigin` | Double fetch | Always add `crossorigin` for fonts |
| Too many preloads (> 5-6) | Bandwidth competition | Prioritize only critical resources |
| Unused preloads | Wasted bandwidth | Remove or verify usage |
| Preconnect without usage | Wasted connection | Only preconnect to used origins |

<Callout type="info">
**Tip:** Preload is for resources needed in the current page. Prefetch is for resources needed in future navigations. Don't confuse them!
</Callout>

### Hints in the Link header

A server can send the same hints in the `Link` response header of the document instead of the HTML, for example `Link: <https://cdn.example>; rel=preconnect`. The browser acts on them before it parses the HTML, and a server or CDN can also send them as a `103 Early Hints` response, while the page is still being generated.

A page cannot read the headers of its own navigation, so the snippet asks for the document again with a `HEAD` request and reads its `Link` header. Each hint says where it was declared (`source`: `dom` or `header`), and a hint declared in both places, or twice in one, is reported once as a duplicate. When the `HEAD` request fails (some servers answer it with `405`), the report covers only the hints of the HTML and says so.

`details.earlyHints` says whether the server sent a `103 Early Hints` response. The browser does not expose which hints that response carried; when it is built from the `Link` header of the document, as a CDN usually does, they are the hints with `source: "header"`.

### One connection per credentials mode

A preconnect opens a connection for one kind of request. Without `crossorigin`, it serves requests that send credentials such as cookies: images, stylesheets and classic scripts. With `crossorigin`, it serves requests that do not: fonts, module scripts, scripts with `crossorigin` and, by default, `fetch()`. A request of the other kind opens a connection of its own, so an origin that serves both kinds needs both preconnects:

```html
<link rel="preconnect" href="https://cdn.example">
<link rel="preconnect" href="https://cdn.example" crossorigin>
```

Resource Timing does not say which kind each request was, so the snippet reads it from the element that made it: the `crossorigin` attribute, `type="module"`, a font in a stylesheet. A request made with `fetch()` or `XMLHttpRequest` can be either, so a preconnect whose origin only gets requests like those is not judged: its `use` is `unknown`.

### When a preconnect does not save the connection

A preconnect only pays off if the request it is for finds the connection still open. Chromium closes an unused preconnected connection after about 60 seconds, and a server or CDN can close one that carries no request much sooner. When that happens, the request opens a connection of its own: the preconnect spent a DNS lookup, a TCP and a TLS handshake early in the load, when the network is busiest, and saved nothing.

Take a page that shows ads and declares both preconnects to its ad server, because the tag script and the ad requests use different credentials modes:

```html
<link rel="preconnect" href="https://ads.example">
<link rel="preconnect" href="https://ads.example" crossorigin>
<script async src="https://ads.example/tag.js" crossorigin="anonymous"></script>
```

- The tag script has `crossorigin`, so it uses the second connection at the start of the load. That preconnect is used.
- The first request with credentials is the ad request, which the tag makes once the user accepts consent and the ad slot is ready: 12 seconds after the start on a slow phone. The connection of the first preconnect has been open for 12 seconds without a request, and the server has closed it. The ad request opens a new connection.

So the first preconnect costs a connection early and gives nothing back. Remove it, or add it when the page knows it is about to make the ad request.

The snippet shows this from Resource Timing. For each preconnect, `firstUseConnection` says what the first request of its credentials mode found: `reused` when it used an open connection, `new` when it opened its own, `cache` when it came from the HTTP cache, and `unknown` when the response has no `Timing-Allow-Origin` header, without which the browser hides the connection phases of a cross-origin request. A `new` connection gets a `preconnect-not-reused` warning.

<Callout type="info">
In the example, the ad request is a `fetch()` with credentials. The snippet cannot tell the credentials mode of a `fetch()`, so the `use` of that preconnect is `unknown` and the snippet says nothing about its connection. Check it in the Network panel of DevTools: right-click the header of the table, add the Connection ID column, and compare the ID of the ad request with the IDs of the earlier requests to the same origin. A new ID on the first request with credentials means it opened its own connection.
</Callout>

### Why preconnect helps

`preconnect` pays off when a resource lives on a third-party origin: it moves the connection setup (DNS, TCP, TLS) off the critical path, so the request can start as soon as the resource is discovered. ### Issues detected

| Issue | Severity | Impact |
|-------|----------|--------|
| Preload missing `as` | Error | Browser can't prioritize correctly |
| Font preload without `crossorigin` | Error | Resource fetched twice |
| Requests without credentials and no `crossorigin` preconnect | Warning | Fonts and modules open a connection of their own |
| Requests with credentials and only a `crossorigin` preconnect | Warning | Images and classic scripts open a connection of their own |
| Unused preload | Warning | Wasted bandwidth |
| Preconnect no request of its mode used | Warning | Wasted connection |
| First request opened a new connection | Warning | The preconnected connection was closed before it |
| Too many preloads (> 6) | Warning | Bandwidth competition |
| Hint declared twice | Info | Nothing, but one of them can go |
| `Link` header not readable | Info | Hints sent only in the header are not in the report |

### Priority guidelines

| Resource Type | Suggested Hint |
|---------------|----------------|
| LCP image | `preload` with `fetchpriority="high"` |
| Critical fonts | `preload` with `crossorigin` |
| Critical CSS | `preload` |
| Third-party scripts | `preconnect` to origin |
| Below-fold images | None (use `loading="lazy"`) |
| Next page resources | `prefetch` |
